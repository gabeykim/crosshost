# Reproducibility Statement

## What `make reproduce` regenerates (fast path — actually run this gate, exit code 0, zero errors)

`make reproduce` regenerates every figure and table in this manuscript from already-computed intermediate results (`out/results/*.json`, `data/*.parquet`) — it does not retrain any model or re-run inference. **Run in full during this gate** (2026-08-19) after extending it to cover Gates 8.5–10.5, which a prior packaging pass had left out of the fast path: it completed with exit code 0, and its own printed output reproduced every GC-confound number in Table S3/S4 of this package bit-for-bit against the numbers already written into the manuscript — an independent regeneration check, not just a read of cached files.

Target now covers, in order: both audit scripts; Gate 6 figures; the crosshost-correlation figure; the feature-ablation figure; the attenuation figures; calibration-figure regeneration; the remaining Gate-7-orphan regeneration; provenance triage; the master baseline export; then (added this gate) the two-stage-transfer table, the conditioning-mechanism comparison, the shift-prediction summary, the co-active range-restriction check, the FiLM fold-variance figure, the Gate 8.6 figures, DRAFTS parsing/joining/correlation/modality/GC-and-floor-check/feasibility, the Gate 10 figures, the in-vivo GC-confound analysis, and the Gate 10.5 figures.

**Deliberately NOT in the fast path** (need a trained-model checkpoint for live inference, or an actual training run — not just cached results): `scripts/78_conditioning_mechanisms.py` (trains concatenation and per-host-head models), `scripts/80_coactive_subset.py` Part 2 (re-scores existing checkpoints via live inference — no training, but does need `.pt` files and a forward pass, categorically different from the pure-table/JSON scripts above), `scripts/81_shift_prediction.py` (trains the shift-prediction architecture), `scripts/84_shift_regression_to_mean_control.py` (imports `scripts/81` as a module; conservatively excluded from the fast path since its import-time cost was not independently verified this gate). Their outputs (CSVs/JSONs already in `out/results/`) are shipped and used by every downstream figure/table script that needs them — you do not need to re-run these four to reproduce anything in this manuscript, only to regenerate their own underlying numbers from scratch.

## What `make reproduce-full` does NOT do (stated plainly, not implied)

`make reproduce-full` re-runs the entire pipeline from raw data, including all CNN and foundation-model training (Gates 4–8). **This was not re-executed end-to-end in this packaging pass, or in any prior one.** It would cost the cumulative 40+ hours of training this project's Gates 4–8 already spent once. The Makefile's dependency graph is accurate and every target maps to a real, working script — each individual script has been run and produced its shipped output at least once (that is how `out/` and `data/` were populated) — but running the full chain consecutively, in one sitting, from raw data alone, has not been attempted through Gate 11. If you need to verify the full pipeline yourself, budget accordingly; do not assume `make reproduce-full` has been smoke-tested end-to-end just because `make reproduce` has.

## What was tested from a genuine fresh clone

**Verified end to end as of Gate 14 (2026-08-19).** Not a fresh venv reusing an existing checkout, not a re-run in place — a literal `git clone https://github.com/gabeykim/crosshost.git` into an empty directory, a fresh `python3 -m venv`, and every subsequent step taken strictly from what the repository's own documentation says, with no step supplied from prior knowledge of the project. `pip install -e ./package`, `pip install -e "./package[citations]"`, `make audit`, `make verify-citations`, and `make reproduce` all pass, with zero undocumented steps, zero manual intervention, and zero numeric deviation from the established values. Full record, including four real defects found and fixed to get there and the exact commands and output at every step: `out/results/gate14_clean_clone_verification.md`.

**What a stranger following only the repository's documentation would have hit before this gate, disclosed in full because it is worth knowing how far off the "reproducible from a clean clone" claim actually was:** no root-level `README.md` existed at all (the only setup documentation, `package/README.md`, was reachable only via the `Makefile`'s own header comment); that file's own "Install" instruction (`pip install -e .`) fails if read literally from the repository root, where there is no `pyproject.toml`; `scripts/audit_leakage.py`'s manifest-hash check failed unconditionally in any clean checkout, because two large source-data bundles are deliberately `.gitignore`d (Gate 10) but the check had no way to know that; and two of this project's own later scripts (`scripts/97_verify_citations.py`, Gate 13, and `scripts/88_parse_drafts.py`, in the fast-reproduce path since Gate 11) depended on packages (`certifi`, `openpyxl`) that were never declared anywhere, present on the development machine only by incidental prior installs unrelated to this project's own declared dependencies — the exact "works on my machine" failure mode a clean-clone test exists to catch. All four fixed; a root `README.md` now exists with the correct setup path, `audit_leakage.py` is gitignore-aware, and both missing dependencies are declared in `package/pyproject.toml`.

**Gate 8.5's own earlier clean-clone claim** (`pip install -e ./package`, `pytest` 9/9 passed, `make audit`, `make reproduce`, all from a fresh clone — `out/state.json` gate_8_5.task4_packaging) **was accurate at the time it was made**, and the regression above was introduced afterward (Gate 10's manifest additions; Gate 11's/Gate 13's new dependencies), then never re-caught because no gate between Gate 8.5 and Gate 14 tested an actual fresh clone — Gate 11 explicitly re-ran `make reproduce` in place, disclosed as such rather than conflated with a clone test. This is why a fresh-clone test needs to be a standing practice, not a one-time claim: it can go stale silently as the codebase changes around it, exactly as it did here.

## Environment

Verified from a genuine fresh clone (Gate 14): **macOS, Apple Silicon (arm64), Python 3.14.2, pip 25.3.** Every pinned dependency in `package/pyproject.toml` had a prebuilt `cp314-macosx-arm64` wheel available — no compilation-from-source step was needed or tested. `environment.lock.txt` records the pinned versions matching the environment this project's own results were produced in. **Not tested on any other OS or Python version** — Linux, Windows, or an older/newer Python than 3.14.2 may behave differently and has not been checked (see Limitations item 6 for the separate, unrelated reason Apple Silicon/MPS-only excluded Evo 2 from this project's model comparisons).
