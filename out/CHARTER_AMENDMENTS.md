# CROSSHOST — Charter Amendments (from Gate 1 and Gate 1.5)

This file is the running list of corrections to `crosshost-PROJECT-CHARTER.md` established by verified evidence. Gate 2 (and everything downstream) should treat this file as authoritative where it conflicts with the original charter text — the charter itself says "if evidence points somewhere other than this plan, say so."

## C1. The leakage defense the charter describes is the wrong one — sequence homology, not barcode replication, is the real vector

**Charter said (Part III Gate 2; Part V rule 1):** the library "contains double-barcoded replicates; barcode-level splitting would leak," making RS-level deduplication (collapsing barcode replicates before splitting) the primary defense, with MMseqs2 clustering as a secondary defense.

**Gate 1 established [VERIFIED]:** the released Supplementary Data Table 1/2 (29,249 oligos actually used for the BS/EC/PA expression data) has **zero** RS-to-multiple-barcode structure — every `OLIGO ID` maps 1:1 to a unique `intgen_id` (genomic locus). The manuscript's described barcode-duplicate QC set (4,778 RSs, n=2,273 pairs in *E. coli*, Pearson r=0.88/0.86) is not reconstructable from the released tables and almost certainly used a separate, unreleased raw dataset.

**Amendment:** Barcode-replicate deduplication is **not applicable** to this table — there is nothing to deduplicate on that axis. The real leakage vector is **sequence homology between regulatory sequences mined from the 184 source genomes**, many of which are phylogenetically related (the library explicitly contains many near-duplicate RSs from related strains — Gate 1 found 181 groups of exactly-identical 165bp sequences across different genomic loci, presumably the tip of a much larger near-identical iceberg once partial-identity matches are counted). MMseqs2 clustering, described in the charter as a secondary defense, is now the **only** defense, and must be treated as load-bearing rather than a nice-to-have.

**Consequence for Gate 2 (mandatory):**
- Report train–test **maximum sequence identity per fold**, not just cluster assignment — cluster assignment alone doesn't reveal how close a near-miss cluster boundary sits.
- Run the identity-threshold sensitivity analysis at **0.3, 0.5, and 0.7** (MMseqs2 `--min-seq-id`), not just the previously-assumed 0.5, and report how the fold structure and per-fold N change at each threshold.
- Report cluster counts per fold at each threshold, so it's visible whether a stricter threshold leaves enough clusters to split into meaningful folds at all (with only 11,276 three-host-usable RSs total, a very strict identity threshold could fragment the data into too many singleton clusters to fold sensibly — this needs to be checked empirically, not assumed).

## C2. Bernstein-lab physiology tables are not a shortcut — remove that assumption

**Charter's Task 4 prompt (Gate 1) suggested checking** whether the Bernstein lab's chassis-effect papers "publish physiological metrics in a reusable form... they may have tabulated exactly what is needed."

**Gate 1 established [VERIFIED]:** their chassis-effect papers (Chan et al. 2023 *BioDesign Research*/bioRxiv 2023.02.27.529268; Chan et al. 2024 *mSystems*/bioRxiv 2024.02.15.580380) never test *B. subtilis* or *P. aeruginosa* — their host panel is *E. coli* plus various environmental Pseudomonads, Halopseudomonads, and *Stutzerimonas* species.

**Amendment:** The Bernstein lab's published **claim** (hosts with similar growth/molecular physiology show similar circuit performance) remains exactly what this project tests — that has not changed and is not in question. But their **data** is not a shortcut and was never going to be: no table from their published work is directly reusable for this project's six hosts. This assumption is removed from the plan. Physiology features must be assembled independently, which is what Gate 1 and Gate 1.5 did.

## C3. Translation N is 7,887, not the paper's 8,898 — use the stricter, reproducible number

**Gate 1 found:** our own reproducible computation of "translation usable in all three primary hosts" (`protein (log10)` not null in BS, EC, and PA simultaneously) gives **7,887** RSs. The paper's own text states a "shared set of 8,898 regulatory sequences" for the same nominal quantity — 89% of our figure, not an exact match. The gap was investigated (see Gate 1 memo, "WHAT I COULD NOT DO") and not resolved; it likely reflects an unstated additional QC step in the paper's own translation-data pipeline that isn't specified in the available Methods text or released columns.

**Amendment:** Use **7,887** as the canonical translation three-host-overlap figure for all Gate 2+ work, because it is the number this project can actually reproduce from code end-to-end. Document both numbers (7,887 computed vs. 8,898 paper-stated) and the discrepancy in any publication. **Do not spend further effort trying to reconcile them** — the gap doesn't change any pass/kill decision (both numbers clear every relevant threshold by a wide margin), so it's not worth the time.

## C4. RS241 usability was computed as the wrong quantity in Gate 1 — corrected in Gate 1.5

**Gate 1 reported:** 111/241 (transcription) and 126/241 (translation) RS241 sequences usable, computed as the **six-way intersection** (usable in all 6 hosts simultaneously), with *B. subtilis* named as the limiting host.

**This was the wrong quantity for the intended use.** Leave-one-host-out evaluation only requires a usable value in the held-out host plus usable values in whichever hosts are actually used for training — not all five other hosts. The six-way intersection is an over-strict filter.

**Gate 1.5 correction [COMPUTED, `scripts/05_task_a_rs241_pairwise.py`]:** per-host counts, the full pairwise usable-in-both matrix, and per-target-host viability were recomputed. Held-out-host viability is substantially higher than 111/126 once training is restricted to a sensible host subset instead of all five others — e.g. held-out *C. glutamicum* with training on {*P. aeruginosa*, *S. enterica*} reaches N=209 (transcription) / 214 (translation), versus N=138/130 when *B. subtilis* is forced into the training set. See the Gate 1.5 memo, Task A, for the full ranked table of runnable configurations.

**Amendment:** The 111/126 six-way-intersection figures from Gate 1 should **not** be used as "the" RS241 usable-N going forward. Gate 5's evaluation design should select training-host subsets per held-out-host target using the Gate 1.5 pairwise/viability tables, not assume all-five-others training. *B. subtilis*'s low RS241 coverage (61.8%) is real and should be excluded from RS241-based training sets when evaluating the three added hosts, since it disproportionately shrinks the usable set for comparatively little information gain (see Gate 1.5 memo Task A for the exact numbers).

## Other findings from Gate 1.5 worth flagging here (not strict "amendments," but material to Gate 2 planning)

- **V. natriegens has no PaxDb entry.** The charter's physiology plan (and Gate 1.5's own Task B) implicitly assumed a single uniform data source (PaxDb) could cover all six hosts. It cannot — PaxDb v6.0's full 405-species list was scanned directly and contains zero V. natriegens datasets (only the unrelated species *Vibrio proteolyticus*). A substitute source (PRIDE PXD027874, a MaxQuant-processed synthetic-biology-motivated V. natriegens proteome) was found and used, but it is a structurally different kind of source (single lab, single study, explicit single growth condition) from the PaxDb-derived data used for the other five hosts. This heterogeneity-of-source-type is now baked into the physiology feature vector and must be disclosed wherever that vector is used.
- ***P. aeruginosa* is the most source-sensitive host in the new omics-proxy approach**, echoing (via a completely independent method) Gate 1's finding that *P. aeruginosa* was the weakest-characterized primary host under the classical growth-law-literature approach. Two reasonable PaxDb dataset choices for *P. aeruginosa* (the "Integrated" aggregate vs. a single 2025 study) disagree by 29–57% relative on every derived metric — far more than the other cross-checked hosts (*B. subtilis*, *S. enterica*, both 9–30% relative). This is now a two-for-two independent signal that *P. aeruginosa* — a **primary** host — is the weakest link in this project's physiology evidence base, not just a Gate-1-specific artifact of literature search difficulty.

## STANDING RULES — Gate 2

Added by Gate 2 (Data Foundation). These apply to every gate from here forward, not just to Gate 2's own outputs.

**SR1. Physiology metrics must be depth-matched or depth-corrected across hosts.** Proteome coverage varies roughly 7-fold across the six hosts (665–5,034 proteins at native depth) and mechanically confounds every abundance-fraction metric — Gate 2's Task 0 depth audit showed ribosomal protein fraction, RNAP core fraction, and chaperone fraction all shift measurably with truncation depth even though their cross-host rank order is preserved (Spearman ρ = 0.83–1.00). Any newly added physiology metric must pass the same depth-sensitivity check (truncate all hosts to a common depth, compare full-depth vs. depth-matched values and rankings) before it is used in any comparison. **Why:** an earlier draft accepted V. natriegens's abundance fractions at face value; the depth audit showed roughly 60% of its apparent "highest ribosomal fraction" margin over the next host was a depth artifact, not biology. **How to apply:** before adding metric X for host comparison, run scripts/10_depth_matching_audit.py-style truncation on X; if the metric can't be computed at a common depth (e.g. it requires deep coverage of rare proteins), flag it as depth-confounded rather than silently reporting it.

**SR2. Provenance flags are mandatory and visible.** Any host whose physiology derives from a different source than the others (currently *V. natriegens*, from PRIDE PXD027874 rather than PaxDb) carries a visible `source` and `proteome_depth` (or `proteome_depth_used`/`proteome_depth_native`) flag in every table, figure, and output that touches physiology data — see `data/hosts_physiology.parquet`'s `physiology_source`, `proteome_depth_native`, and `proteome_depth_used` columns for the pattern to follow. **Why:** V. natriegens's absence from PaxDb (verified by scanning the full 405-species list, Gate 1.5) is a structural, not incidental, difference in how its numbers were produced, and it happens to be one of the six hosts most likely to be discussed as a headline result (fastest-growing organism, highest ribosomal fraction). **How to apply:** never merge physiology tables in a way that drops the source/depth columns; never report a cross-host physiology comparison without a footnote on source heterogeneity.

**SR3. Within-host quantile normalization is fit on training folds only, inside the fold loop. Never globally.** `scripts/audit_leakage.py` asserts this (check 5) — currently a structural check for the absence of any global-statistic artifact in the frozen `data/` tables, since no normalization code exists before Gate 3; the check must be extended once Gate 3 introduces the actual fit/transform code to verify the fit function is called once per fold with only that fold's training data. **Why:** this was already charter Part V rule 2; restated here as a standing rule specifically because it is now mechanically enforced rather than only written down. **How to apply:** any normalization, scaling, or statistic (mean, std, quantiles, PCA components, etc.) used as a model input must be computed inside the fold loop on the training partition only, and never touch validation/test data for that fold.

**SR4. Exact-duplicate sequences must be co-assigned to the same fold — checked explicitly, never assumed to follow from clustering.** Added in direct response to a Gate 2 finding: mmseqs2 clustering (both `easy-cluster` and `easy-linclust`, the only two modes that ran successfully in this environment) failed to co-cluster at least one pair of byte-identical 165bp sequences (OLIGO 21865/37869, same source genome) even at `--min-seq-id 0.7`. A broader all-pairs identity audit (Gate 2 Task 3.4) subsequently found clustering also misses many near-duplicate (85–93% identity) and "shifted" duplicate (identical after a small indel-sized register shift) pairs that a naive reading of "clustered at 0.7" would assume were handled. **Why:** approximate/linear-time clustering tools trade completeness for speed and memory and carry no formal guarantee that every high-identity pair is merged — this is a real, demonstrated gap for this dataset, not a hypothetical. **How to apply:** every split-freezing step must run an explicit all-pairs (or at minimum all cross-fold-candidate) near-duplicate check via an independent method (e.g. the k-mer-index + exact/shift-tolerant identity check in `scripts/24_final_split_with_near_dup_net.py`) and force-merge any connected component that spans multiple folds — do not trust clustering output alone, regardless of which identity threshold was requested.

**Headline methodological result to carry into the paper:** after the full treatment above (genome-blocked primary split + exact-duplicate safety net + near-duplicate safety net at ≥0.85 identity), **maximum train-test sequence identity is ≤0.8485 across all 5 folds** (fold-by-fold: 0.8485, 0.8395, 0.8485, 0.8485, 0.8364). Benchmarks in this space rarely report this figure at all; reviewers who know this dataset (184 source genomes, some phylogenetically close, per Gate 1) will ask for it. Report it as a number, not a claim of "clustering was applied."

## FINDINGS — Gate 3 (Baselines)

**Finding: the translation floor-value artifact is a first-class data limitation, not a footnote.** `protein_log10` (the translation-strength regression target) is pinned at a per-host floor/pseudo-value for **66.5%** (*E. coli*), **89.9%** (*B. subtilis*), and **10.1%** (*P. aeruginosa*) of otherwise-"usable" rows — almost certainly the paper's own below-detection-limit convention, not real quantitative measurements (Gate 3, `scripts/28_prepare_baseline_data.py`). After excluding floor-pinned rows from the regression target, **usable translation-regression N is 9,146 (EC) / 1,101 (BS) / 17,630 (PA)** fold-wide — an order of magnitude smaller than the raw "usable" column implies for *B. subtilis* specifically (11,564 raw vs. 1,101 real). **Why this matters:** any Gate 4+ work, and the eventual paper, that reports "N usable translation examples" without this correction overstates *B. subtilis*'s translation data by ~10.5×. **How to apply:** every subsequent gate's translation-readout work must use the floor-corrected counts (cached per-host in `data/baseline_cache/*.npz` as `tl_usable_for_regression`), and the paper must report both the raw and floor-corrected N side by side with the floor fraction, exactly as Gate 3 did.

**Finding: mechanistic asymmetry between readouts — transcription has recoverable biophysical signal from a single simple feature, translation does not.** Sigma-70 promoter motif match score carries real transcription signal on held-out data (Spearman ρ = 0.24–0.43 across the three primary hosts), while UTR folding free energy (ΔG) alone carries essentially none for translation (|ρ| < 0.02 for all three hosts) (Gate 3, `scripts/33_baseline4_biophysical.py`, evaluated on the same frozen test fold as every other baseline — a genuine measurement, not a literature quote). **Why this matters:** this is a reportable scientific result in its own right, not just a diagnostic — it says the transcription layer has sequence grammar a single motif-match feature already partially captures, while translation initiation strength requires more than folding energy alone (the full RBS Calculator combines ΔG with anti-SD hybridization and spacing, which this baseline omits by construction). It also sets a prior for Gate 4: host conditioning is more likely to show a clean win on transcription, where the biophysical signal is already partially legible, than on translation, where even the paper's own biophysical proxy is uninformative alone. **How to apply:** do not expect symmetric host-conditioning gains across readouts in Gate 5; report transcription and translation results separately with this prior stated, not pooled into one headline number.

## STANDING RULES — Gate 3.5

**SR5. Single-fold baseline results are not trustworthy on their own — fold-to-fold variance must be checked against draw-to-draw variance before quoting a point estimate.** Gate 3.5 re-ran B1–B4 across all 5 folds (Gate 3 used fold 0 only) and found **fold-to-fold standard deviation exceeds within-fold draw-to-draw standard deviation in 15 of 23 (host, readout, N) combinations checked for B2 alone** — and the ratio grows sharply with N (e.g. *E. coli* transcription at N=3000: fold std=0.060 vs. draw std=0.0007, a 91× ratio) precisely because averaging over 10 draws shrinks draw noise while doing nothing about which 80/20 split you happened to train/test on. **Why:** a single fixed test fold (as Gate 3 used throughout, for compute-budget reasons) can look highly "precise" (tight draw-to-draw error bars) while still being an unrepresentative sample of the true host-level performance, because the precision it shows is about the wrong source of variance. **How to apply:** any baseline or model number intended for the paper (not just an internal sanity check) must report variance across folds, not only across random draws within one fold; where full 5-fold rotation isn't affordable (e.g. CNN fits), state explicitly that fold variance was not checked and flag the number as provisional.

**SR6. When a task specifies "N calibration examples," resolve explicitly whether N means measured parts (nominal, includes non-informative outcomes) or informative training rows (effective, post-filtering) before reporting a headroom/data-floor verdict.** Gate 3.5 Task 1 found these two framings disagree by an order of magnitude for *B. subtilis* translation: Gate 3's B2 draws N from the full measured-parts pool (9,300/fold), where only ~10% turn out non-floor/regression-informative, so nominal N=100 yields only ~10 effective regression rows (unstable, ρ=0.07±0.18) while nominal N=3000 yields ~300 effective rows (ρ=0.289±0.010, essentially the same as sampling 300 rows directly from the regression-informative-only pool). **Why:** conflating the two framings produces a false "the N=3,000 arm doesn't exist" conclusion when it is actually the effective-regression-N framing, not the nominal-measured-parts framing, that is data-limited — and the nominal framing is the one that matches both the charter's own "measure N parts in your host" language and Gate 3's actual implementation. **How to apply:** state which N definition is in use whenever reporting a calibration-cost curve for a low-activity-rate host/readout combination, and report the discovery/activity rate alongside the curve so a reader can convert between the two.

## STANDING RULE — Gate 7

**SR7. All model inference is internally chunked at ≤1024 rows; unbatched forward passes over large arrays hit a severe non-linear performance cliff on both MPS and CPU.** Found while building Gate 7's conformal-calibration script, the first script in this project to call `predict_seqonly`/`predict_film` on a large pooled array (a held-out host's ~23,232-row calibration set) rather than a single ~5,800-row LOHO test fold. Measured directly: 5,810 rows in 28.5s (unbatched) vs. 23,232 rows (4× the data) in 8,454s (unbatched) — roughly 300× the cost for 4× the data, not linear. This is the same shape of pathology Gate 4 documented for MPS batch sizes above ~2048 (a ~30× cliff), now confirmed on CPU as well, and traceable to the same root cause: a single unbatched `model(X)` forward call with no internal chunking. **Fix:** `predict_seqonly` (`scripts/58`) and `predict_film` (`scripts/40`) now chunk internally at `batch_size=1024` (overridable), verified numerically identical to the unbatched path to float32 precision (max abs diff 7.15e-07, `scripts/audit_batching_fix.py`) and benchmarked at 73.6× faster for the 23,232-row case, with scaling restored to roughly linear (4× rows → 4.37× time). **Why this didn't corrupt any prior gate's results:** every call site in Gates 1–6 passed at most 5,818 rows (one LOHO test fold, the 207-row RS241 set, or a 500-row sanity slice) — all within the pre-cliff "fine" zone (a checked, not assumed, fact — see `out/GATE7_MEMO.md` Task A for the full call-site audit). Those runs were slow relative to what they could have been, but not wrong. **How to apply:** any new evaluation code that pools multiple folds or hosts into one array before calling either predict function must use the chunked path (now the default) rather than assume a single-fold-sized input; if a future array is expected to exceed a few thousand rows, benchmark before committing to an unattended multi-hour run.
